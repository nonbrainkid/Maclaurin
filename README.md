# $MACLRN — реализация фаз 1, 2 и 4

ERC-20, у которого график эмиссии буквально является рядом Маклорена для `e^x` в точке x=1.
Эпоха `n` выпускает ровно `1e27 / n!` wei. Сумма всех эпох = `e × 10^27` = общий сапплай.
Ряд сходится → сапплай ограничен математически, а не обещанием команды.

> Ряд Маклорена — это ряд Тейлора, разложенный в нуле. Наш ряд `e = Σ 1/n!` —
> ровно такой: разложение `e^x` в точке a=0, взятое при x=1. Отсюда и имя токена.

Реализация по [MACLAURIN-TOKEN-SPEC.md](MACLAURIN-TOKEN-SPEC.md).

| Фаза | Что это | Состояние |
|---|---|---|
| 1 | Таблица эпох + стейкинг + учёт остаточного члена | **реализована** |
| 2 | Radius of Convergence — локи и множители наград | **реализована**, см. [PHASE2-SPEC.md](PHASE2-SPEC.md) |
| 3 | Lagrange Remainder Vault — контракт-казна на месте `remainderVault` | не реализована; `remainderVault` — обычный адрес `0x6d8137E5…cc07`, **зафиксированный мейннет-деплоем навсегда**: фаза 3 обязана встать ровно на него |
| 4 | Бондинг-кривая + казна под замком + раскладка genesis | **реализована**, см. [PHASE4-SPEC.md](PHASE4-SPEC.md). Аудит нашёл критическую дыру; закрыта именным правом выкупа, фикс проаудирован отдельно |

Фаза 2 сделана **до** мейннета, вопреки исходному порядку из спецификации. Причина
записана в [LAUNCH-PLAN.md](LAUNCH-PLAN.md) §0.2: контракт неизменяем, а тезис
«максимальный множитель равен `e` и недостижим» — половина нарратива. Добавить
механику после деплоя было бы невозможно.

**Проект запущен в мейннете.** Сеть — **Robinhood Chain** (chain ID 4663,
Arbitrum Orbit L2). Тестнет (46630) пройден и остался позади, см. «Тестнет» ниже.

## Эмиссия: ряд Маклорена как график выпуска

```
TOTAL_SUPPLY   = 2718281828459045235360287471  wei   // floor(e × 10^27)
GENESIS        = 2000000000000000000000000000  wei   // члены n=0 и n=1
EMISSION_POOL  =  718281828459045235360287471  wei   // хвост ряда, n ≥ 2
```

`GENESIS` (73.576% сапплая) минтится в конструкторе на один адрес и не фармится.
`EMISSION_POOL` (26.424%) лежит в `MaclaurinEmission` и раздаётся по эпохам.

- `EPOCH_DURATION = 7 days`
- `FIRST_EPOCH = 2`, `LAST_EPOCH = 26` → `EMISSION_DURATION = 175 дней`
- награда эпохи `n` — константа из таблицы `epochAmount(n)`, равная `1e27 / n!`
- на эпохе 27 `1e27 / 27!` даёт ноль при целочисленном делении → **эмиссия
  заканчивается свойством арифметики uint256, а не решением мультисига**

Факториал не считается циклом: таблица из 25 предвычисленных значений сверена
построчно с §2.1 спецификации тестом `test_EpochTable_MatchesSpec`.

### Проверка констант

Все числа из §2 спецификации пересчитаны офчейн независимо (Python, `decimal`
с 60 знаками) перед тем, как попасть в контракт:

```
floor(e × 10^27)      = 2718281828459045235360287471   OK
GENESIS (1/0! + 1/1!) = 2000000000000000000000000000   OK
EMISSION_POOL         =  718281828459045235360287471   OK
Σ эпох 2..26          =  718281828459045235360287457   OK
пыль (остаточный член)= 14 wei                         OK
1e27 / 27!            = 0  → эмиссия завершается сама  OK
```

Эти же равенства проверяются повторно после деплоя, на цепочке, в `_verify()`
скрипта `Deploy.s.sol`.

## Radius of Convergence (фаза 2)

Каждый ряд сходится лишь внутри своего радиуса. Стейкер выбирает радиус `R` —
число эпох, на которое лочится позиция. Множитель наград равен **частичной сумме
того же ряда до `R`-го члена**.

| R | Лок | `multiplier(R)` (1e18 fixed-point) | Значение | Прирост |
|---|-----|------------------------------------|----------|---------|
| 1 | 7 д  | `1000000000000000000` | 1.000000 | — |
| 2 | 14 д | `2000000000000000000` | 2.000000 | +1/1! |
| 3 | 21 д | `2500000000000000000` | 2.500000 | +1/2! |
| 4 | 28 д | `2666666666666666666` | 2.666667 | +1/3! |
| 5 | 35 д | `2708333333333333333` | 2.708333 | +1/4! |
| 6 | 42 д | `2716666666666666666` | 2.716667 | +1/5! |
| 7 | 49 д | `2718055555555555555` | 2.718056 | +1/6! |

`MAX_RADIUS = 7`. Прирост множителя между соседними радиусами — это ровно члены
`1/n!` того же ряда, то есть отдача убывает факториально. После R=7 спор идёт
за 0.0002 множителя.

**Потолок — `E_FIXED = 2718281828459045235` (`floor(e × 1e18)`), и он недостижим
ни при каком R:** частичная сумма строго меньше суммы ряда. Константа лежит
в контракте именно затем, чтобы это можно было проверить на цепочке
(`test_Multiplier_NeverReachesE`), а не принимать на слово.

### Вес вместо принципала

Награда делится не по стейку, а по весу:

```
weight(user) = staked(user) * multiplier(radius) / 1e18
totalWeight  = Σ weight(user)
```

`totalStaked` остаётся отдельным счётчиком принципала и участвует в инварианте
платёжеспособности — множитель не имеет никакой возможности повлиять на возврат
тела депозита.

### Почему лок висит на `claim()`, а не на `unstake()`

Наивная схема (множитель сразу, `claim()` открыт всегда, за досрочный выход
штраф) не работает вообще:

```
1. stake(1000, R=7)      -> множитель 2.718x
2. ждём эпоху, claim()   -> награда с бустом уже выведена из контракта
3. повторяем каждую эпоху
4. unstake досрочно      -> штраф сжигает rewards[user], а там 0
```

Атакующий получает 2.718x, не отсидев ни одного лока: к моменту штрафа отбирать
нечего. Поэтому:

- `claim()` до `unlockTime` ревертит `StillLocked(unlockTime)`;
- `unstake()` открыт **всегда**, включая активный лок, и возвращает принципал
  целиком, до последнего wei;
- досрочный выход обнуляет `rewards[user]` и переводит их в `unallocated`
  (казна остаточного члена), событие `RewardForfeited`.

Награда сгорает целиком даже при частичном выходе. Пропорциональное сжигание
выглядело бы справедливее, но открывало бы дробление: выйти телом на 99.99%,
оставить пыль и досидеть лок пылинкой, сохранив награду, набранную полным телом.

Запереть награду навсегда нельзя: `unlockTime` ≤ момент стейка + 49 дней,
а полный выход из позиции удаляет её вместе с локом.

### Одна позиция на адрес

```solidity
struct Position { uint256 staked; uint256 radius; uint256 unlockTime; uint256 weight; }
mapping(address => Position) public positions;
```

Массив позиций с разными радиусами потребовал бы цикла при клейме — неограниченный
газ и DoS на самого пользователя. Кому нужны разные радиусы, использует разные
адреса и платит за это своим газом.

Повторный `stake` в активную позицию разрешён с двумя условиями:

1. новый `R` **не меньше** текущего, иначе `RadiusCannotDecrease` — иначе лок
   можно было бы разбавить: набрать множитель на большой сумме с R=7, докинуть
   wei с R=1 и уехать через неделю всей позицией;
2. `unlockTime` пересчитывается **от текущего момента**, а не продлевается от
   старого, — иначе докидывание пыли за день до разлока давало бы полный
   множитель на новую сумму за сутки реального обязательства.

Вес пересчитывается на весь новый объём. `stake` требует `amount > 0`, поэтому
поднять радиус, не добавив хотя бы 1 wei, нельзя.

### `poke(address)` — сброс истёкшего буста

После `unlockTime` пользователь ничем не рискует, но вес всё ещё умножен.
Автоматически пересчитать нельзя: кипера в системе нет и не будет, а перебирать
стейкеров циклом — неограниченный газ.

`poke(user)` permissionless: сбрасывает радиус и вес позиции до 1.0x, если лок
истёк. Это **не** админское полномочие — адрес не выбирается (условие проверяется
на цепочке), сумма не выбирается, новый вес однозначен.

- активный лок → `StillLocked`
- позиции нет → `NoPosition`
- радиус уже 1 → `AlreadyAtBaseline`

Стимул звать её есть у любого другого стейкера: снижение чужого веса поднимает
его собственную долю в `totalWeight`.

Осознанный компромисс: пока `poke` никто не позвал, вес завышен. Это
перераспределение между стейкерами, а не потеря для протокола — суммарные
выплаты по-прежнему ограничены суммой ряда.

## Бондинг-кривая (фаза 4)

Пул ликвидности требует капитала, которого нет: $14 в пуле дают глубину, при которой
покупка на $3 двигает цену на 47%. Кривая капитала не требует вообще — резерв возникает
из денег покупателей и уходит вместе с ними. Побочный эффект решает главную проблему
проекта: те самые 73.576% genesis перестают лежать на кошельке создателя и становятся
товаром в контракте, откуда их нельзя достать иначе как купив.

Цена линейна по количеству уже проданного, стоимость сделки — площадь трапеции.
Только целочисленные умножение и деление, ни одного приближения:

```
p(x) = P0 + SLOPE·x / INVENTORY

INVENTORY   = 1 000 000 000e18 токенов
P0          = 200 000 000 000 000 000        ценовых единиц за wei токена
P_FINAL     = 543 656 365 691 809 047        = P0 × e, деление точное
TOTAL_RAISE = 3 718 281 828 459 045 235 wei  = (1 + e) ETH
```

**Где здесь `e`.** Коэффициенты подобраны так, что при распродаже всего инвентаря цена
растёт **ровно в `e` раз**: `P_FINAL × 1e18 / P0 == E_FIXED` без остатка. Это одно
деление на цепочке, а не обещание. Побочно вышло второе точное равенство: весь
инвентарь стоит ровно `(1 + e)` ETH. Цена одного целого токена — от 2 gwei до
5.436563656 gwei.

Комиссия — **1% в ETH, с обеих сторон, константа**. Она **никогда не берётся из
резерва**: при покупке изымается до зачисления в резерв, при продаже — из суммы, уже
вычтенной из резерва. `reserve` и `feesAccrued` — раздельные счётчики, и ни одна строка
их не смешивает.

### Кривая — не биржа, и это её ключевое свойство

Продать в кривую можно **ровно то, что этот адрес у неё купил** — счётчик
`boughtOf[address]` растёт при покупке и гасится при возврате. Токены, полученные не от
кривой (награды стейкинга, доли genesis, покупка у другого держателя), продаются на
вторичном рынке.

Это не ограничение продажи, а условие того, что резерв вообще принадлежит покупателям.
Без именного учёта достаточно проверки `amount <= sold` — и тогда право на резерв
получает не тот, кто его наполнил, а любой, у кого есть нужное число токенов:

```
1. Покупатель вносит 1 ETH        -> reserve ≈ 0.99 ETH, sold = 374 503 207…
2. Держатель доли genesis (он не платил кривой ничего) продаёт столько же
                                  -> забирает 0.9801 ETH, reserve = 1 wei, sold = 0
3. Покупатель зовёт sell()        -> РЕВЕРТ: sold уже ноль
```

Формально инвариант выполнен — просто инвариант был не тот. Масштаб не гипотетический:
вне кривой сразу после раскладки лежит 250 млн токенов, и ещё 718 млн эмиссия постепенно
раздаст стейкерам — против инвентаря кривой в 1000 млн.

### Чего в кривой НЕТ

Нет `owner` и ролей, нет паузы, нет апгрейда, нет функции спасения токенов или ETH,
нет `receive`/`fallback`, нет ни одной функции, способной тронуть `reserve` иначе как
через продажу токенов обратно. У `sell` нет ни одного условия сверх арифметически
необходимых: ни кулдауна, ни белых/чёрных списков, ни налога на продажу, ни чьей-либо
подписи. Обратное — определение honeypot.

**Никаких расчётов от `address(this).balance`:** прислать ETH принудительно может любой
(`selfdestruct` долетает и без `receive`), и если бы резерв читался как баланс, донат
двигал бы цену. То же правило действует в `MaclaurinEmission` относительно `balanceOf`.

**Округление всегда в пользу протокола:** покупка платит вверх (`_costCeil`), продажа
получает вниз (`_costFloor`). Отсюда `reserve ≥ A(0, sold)` после любой
последовательности сделок — площадь аддитивна, а обе границы округляются в одну сторону,
поэтому дробление сделок ничего не ломает. Выплатить больше, чем лежит в резерве,
невозможно арифметически.

### Анти-снайп — смягчение, а не защита

`ANTI_SNIPE_WINDOW = 1 hours` от развёртывания кривой, `ANTI_SNIPE_MAX = 1%` инвентаря
(10 000 000 токенов, около 0.0202 ETH) на адрес. Лимит считается по адресу и **обходится
несколькими кошельками** — говорить о нём надо ровно так. Он делает одно: снайпер,
скопировавший транзакцию развёртывания, не может выкупить существенную долю инвентаря
одной транзакцией в первом же блоке.

Отсюда жёсткое требование к деплою: инвентарь обязан быть переведён в кривую **в том же
прогоне**, что и её развёртывание. Если между ними пройдёт больше часа, окно истечёт до
начала торгов и смягчение не сработает вообще (`RELEASE-CHECKLIST.md` §1.2).

## Казна под замком (фаза 4)

`MaclaurinVesting` держит 500 000 000 токенов и отдаёт их бенефициару не раньше
`unlockTime` — целиком, одной операцией. Дата одна: `startTime` эмиссии + 175 дней,
то есть конец полного цикла эмиссии. Ступенчатый график по ряду `1/n!` обсуждался и
отклонён: каждая дополнительная ветка — ещё одно место, где может быть спрятана ошибка.

В мейннете это `unlockTime()` = `1800970780` (2027-01-26 13:39:40 UTC), ровно
`startTime()` эмиссии + `15 120 000`. Сегодня `release()` ревертит `StillLocked`
с этим же числом в аргументе — проверяется одним `cast call`.

Ключевое свойство — то, чего в контракте нет:

- нет функции досрочного вывода — ни для деплоера, ни для кого;
- нет `owner`, нет ролей, нет `Ownable`;
- нет способа сменить `beneficiary` или подвинуть `unlockTime` — все три поля immutable;
- нет proxy, нет `selfdestruct`, нет произвольного `call`;
- нет `receive`/`fallback` — контракт не принимает ETH.

Обычный «вестинг» на рынке — это контракт с `emergencyWithdraw() onlyOwner`: юридически
всё честно, функция задокументирована, а на практике казна разблокирована с первого дня.
Здесь отличать нечего: функции нет в байткоде, и это проверяется сканированием селекторов
в тесте.

`release()` открыт для всех: получатель зашит в immutable, поэтому «кто нажал» не влияет
ни на сумму, ни на адрес. `onlyBeneficiary` не добавил бы безопасности, зато добавил бы
способ отказа — если бенефициаром окажется мультисиг, неспособный отправить произвольный
вызов, казна осталась бы запертой навсегда.

## Раскладка genesis

Решена, **захардкожена константами** в [`script/Distribute.s.sol`](script/Distribute.s.sol)
(долю нельзя подменить переменной окружения) и **выполнена в мейннете** одним прогоном —
фактические балансы с цепочки в разделе «Мейннет» вверху. Геометрический ряд
`2 = 1 + 1/2 + 1/4 + …`, без остатка (таблица — [PHASE4-SPEC.md](PHASE4-SPEC.md) §7):

| Доля | Токенов | Куда | % сапплая |
|---|---:|---|---:|
| 1/2 | 1 000 000 000 | инвентарь `MaclaurinCurve` | 36.79% |
| 1/4 | 500 000 000 | `MaclaurinVesting`, казна | 18.39% |
| 1/8 | 250 000 000 | сжигается в `0x…dEaD` | 9.20% |
| 1/16 | 125 000 000 | маркетинг и эйрдропы | 4.60% |
| 1/32 | 62 500 000 | резерв | 2.30% |
| хвост | 62 500 000 | остаточный член, `REMAINDER_VAULT` | 2.30% |

Хвост геометрического ряда с шагом ½ равен последнему выписанному члену — это свойство
ряда, а не подгонка. Сумма — ровно 2 000 000 000.

Итоговая картина сапплая: 36.8% продаётся людям через кривую, 26.4% раздаётся стейкерам
(уже в `MaclaurinEmission`, создателю недоступно), 18.4% в казне под вестингом, 9.2%
уничтожено, 6.9% маркетинг и резерв, **на личном адресе создателя — ноль**. Скрипт
проверяет это пост-условием: `sender balance is zero`.

Адрес сжигания — `constant` в байткоде скрипта, а не переменная окружения. Настраиваемый
«адрес сжигания» — известный способ оставить себе 9.2% сапплая, не поменяв в документации
ни строчки.

**Доли под пул ликвидности в раскладке нет:** её заменила кривая. Пул Uniswap —
необязательный шаг после запуска, из доли маркетинга или резерва.

## Свойства безопасности

Проверено тестами, а не декларировано.

| Требование §6 спеки | Как закрыто |
|---------------|-------------|
| Функции `mint` не существует | `test_NoPrivilegedFunctionsInBytecode` — поиск селекторов в **развёрнутом байткоде**, а не «вызов реверит» |
| `Ownable` не используется | Селекторы `owner()`, `transferOwnership` отсутствуют в байткоде |
| Нет proxy/upgradeable | `upgradeTo` отсутствует; контракт не за прокси |
| CEI в `claim()`/`unstake()` | Обнуление до `transfer` + `ReentrancyGuard`; `test_Reentrancy_ClaimCannotBeDrained` |
| Константы предвычислены | Таблицы эпох и множителей — литералы, ни факториал, ни частичные суммы не считаются в рантайме |
| Округление в пользу протокола | Вес считается вниз, аккумулятор делится вниз; `invariant_ContractIsAlwaysSolvent` |
| Нет оракулов и киперов | Единственный внешний вход — `block.timestamp`. `poke` — не кипер: её никто не обязан звать, и она ничего не выбирает |
| `SafeERC20` везде | Все переводы через `safeTransfer`/`safeTransferFrom` |

Отдельно проверены классы атак, которых нет в §6, но которые бьют по стейкингу:

| Класс | Результат |
|-------|-----------|
| **Обход лока (главная дыра фазы 2)** | 7 независимых проб в `test/Phase2Probe.t.sol`: клейм до разлока, `poke` для досрочного разлока, `exit` + попытка вернуть сгоревшее, частичный выход, доливка в конце лока. Буст нельзя вывести, не отсидев лок |
| **Flash loan** | Занять → застейкать → заклеймить в одной транзакции даёт **ноль**. Аккумулятор двигается только временем, а `userRewardPerTokenPaid` фиксируется в момент стейка → delta == 0 |
| **Donation / inflation** | Прямой перевод токенов на контракт не меняет ничьи награды — `balanceOf` не участвует в расчётах |
| **Ретроактивный захват** | Опоздавший с огромным стейком получает 0 за прошедшие эпохи |
| **Переполнение на краях** | `test_MaxWeight_NoOverflowAndTailSurvives`: весь сапплай в стейке с максимальным множителем не переполняет `weight * delta` и не обнуляет хвост ряда |
| **DoS длинным простоем** | Цикл идёт по эпохам, не по секундам, и обрывается на `emissionEnd` → максимум 25 итераций |

**Инварианты** (каждый — 256 прогонов × 64 действия, 0 ревертов):

- контракт всегда платёжеспособен: покрывает принципал + всю начисленную награду;
- принципал стейкеров никогда не расходуется;
- сумма выплат никогда не превышает сумму ряда;
- `totalSupply()` неизменен при любой последовательности действий;
- учёт стейков сходится; учёт весов сходится;
- `weight == staked * multiplier(radius) / 1e18` для каждой позиции;
- вес позиции не меньше тела и не больше `тело × e`;
- аккумулятор монотонно неубывающий;
- после `emissionEnd` сумма выплат и свипов не превышает сумму ряда.

Отдельно: **`balanceOf(address(this))` не используется в расчётах нигде.** Контракт
держит пул эмиссии и принципал стейкеров в одном и том же токене, поэтому расчёт
от баланса был бы дырой — чужой donation раздувал бы награды, а принципал стал бы
выплачиваемым.

### Кривая и казна (фаза 4)

Инварианты кривой — 13 штук, тот же режим 256 прогонов × 64 действия:

- резерв покрывает выкуп **всего** проданного (`invariant_ReserveCoversFullBuyback`);
- баланс контракта покрывает резерв **и** невыведенную комиссию — комиссия не съедает
  резерв (`invariant_FeesNeverEatReserve`, `invariant_BalanceCoversReserveAndFees`);
- `sold` никогда не превышает `INVENTORY`;
- **`Σ boughtOf[всех] == sold`** — тот самый инвариант, из которого следует, что право
  выкупа именное и суммарно равно выпущенному;
- продажа без покрытия не проходит никогда (`invariant_UnbackedSellNeverSucceeds`);
- учёт ETH сходится: приход − расход == `reserve + feesAccrued + feesWithdrawn`;
- цена монотонна по сделкам, круг «купил-продал» **всегда** убыточен;
- превью совпадает с исполнением; счётчик комиссии только растёт; цена не выходит
  за `[P0, P_FINAL]`.

Плюс 7 независимых проб в `test/CurveProbe.t.sol`, написанных против кривой, а не для
неё: последнему продавцу всегда хватает резерва; обратный порядок выхода тоже работает;
круг убыточен; **принудительно присланный ETH не двигает цену**; вывод комиссии не может
обесточить резерв; дробление покупок не даёт преимущества; **посторонний не может увести
резерв покупателя** — та самая атака, ради которой существует `boughtOf`.

Казна закрыта 19 тестами, и главный из них — сканирование селекторов в развёрнутом
байткоде: функции досрочного вывода там нет, как нет `owner()` и `transferOwnership`.

### Что нашёл аудит фазы 4

Это самая полезная страница в репозитории, потому что она про то, как **выполненный
инвариант и зелёный фаззер ничего не гарантировали**.

Аудит фазы 4 вернул находку с оценкой **Medium** — «проблема доступности». При проверке
она оказалась **критической**. Воспроизведено тестом:

```
1. Покупатель вносит 1 ETH
   -> reserve ≈ 0.99 ETH, sold = 374 503 207 786 020 143 771 730 036
2. Держатель genesis-доли — он не платил кривой ничего — продаёт ей столько же
   -> забирает 0.9801 ETH, reserve = 1 wei, sold = 0
3. Покупатель вызывает sell(...) -> РЕВЕРТ: sold уже ноль
   -> вернул 0 ETH и остался с 374 млн токенов на руках
```

#### Почему это не поймал инвариант платёжеспособности

Инвариант **выполнялся на каждом шаге**. Обязательство кривой равнялось `sold`, резерв
его покрывал, ни одна проверка не сработала, вычитание нигде не ушло в минус. Просто
инвариант был **не тот**: он был сформулирован про контракт, а не про человека.

> «Контракт всегда может выплатить по всем выпущенным токенам» — истинно.
> «Покупатель всегда может забрать свои деньги» — ложно.

Между этими двумя утверждениями помещается потеря всего депозита покупателя. Разница в
том, что `sold` **глобален**: он не знает, чьи это токены, а токен фунгибелен и памяти
о происхождении не несёт. Право на резерв получал не тот, кто его наполнил.

Отсюда `boughtOf` — именное право выкупа, растущее только в `buy()` на того, чей ETH лёг
в резерв. Фикс проаудирован отдельным проходом (Critical/High/Medium/Low — ноль, два
Info) и подтверждён независимой пробой `test_probe_OutsiderCannotStealBuyerReserve`.

#### Почему это не поймал фаззер

Инвариантов было десять, каждый на 256 прогонов × 64 действия — **16 384 вызова**, ноль
падений. И **слепота к целому классу атак по построению**: хендлер выбирал объём продажи
как `min(balanceOf(actor), sold)`, а все акторы владели только тем, что сами купили у
кривой. Значит «продать чужое» не выпадало **ни разу** — не потому что это безопасно, а
потому что генератор такой сценарий не порождал.

Мораль, применимая ко всему остальному в этом репозитории: **фаззер проверяет только те
состояния, до которых умеет дойти его хендлер.** Зелёный инвариант — это утверждение о
покрытии хендлера, а не о контракте. Поэтому в проекте есть отдельные файлы проб
(`test/CurveProbe.t.sol`, `test/Phase2Probe.t.sol`), которые пишутся **против** контракта
и не переиспользуют его хендлеры, а также символьные проверки, где состояние задаётся
напрямую и вопрос «дойдёт ли туда генератор» не возникает вовсе.

### Два бага, найденных в фазе 1

Оба — из класса, о котором предупреждает §6.6 спеки: не ошибка компиляции,
а тихо неверная экономика. И оба убивали именно хвост ряда.

1. **Масштаб аккумулятора.** При `1e18` эпоха 26 выплачивала 0 wei вместо 2
   (`2 * 1e18 / 1e21 == 0` при стейке в 1000 токенов), полный цикл терял 13 457 wei.
   Масштаб поднят до `ACC_PRECISION = 1e30`. Регрессия —
   `test_EveryEpoch_PaysItsExactSeriesTerm`.
2. **Округление до перевода в единицы аккумулятора** (нашёл Slither,
   `divide-before-multiply`). Награда отрезка округлялась до целых wei **до**
   умножения на масштаб; для эпохи 26 отрезок в 2 секунды давал `2 * 2 / 604800 == 0`,
   то есть любой, кто дёргает контракт каждый блок, стирал хвост эмиссии.
   Регрессия — `test_FragmentedAccrual_DoesNotDestroyTail`; проверено, что на старом
   коде тест падает `0 != 2`.

Обе границы `ACC_PRECISION` пересчитаны под вес фазы 2 (делитель — `totalWeight`,
а он до 2.718 раза больше принципала) и подтверждены независимым аудитом:

| Величина | Значение |
|---|---|
| Максимальный вес (весь сапплай под R=7) | 7.388e27 |
| Инкремент аккумулятора на эпохе 26 при максимальном весе | 270 (в фазе 1 — 735) |
| Запас `weight × delta` до потолка uint256 | ×1.61e20 |

Снизу запас сократился ровно втрое и остался с двумя с лишним порядками до нуля —
хвост ряда не обнуляется. Сверху множитель оценку не сдвигает вообще: он входит
и в числитель, и в знаменатель, и сокращается. `1e30` менять не потребовалось.

### Slither

```bash
slither .
```

Настройки в `slither.config.json`, флаги в командной строке не нужны. Прогон
на 17 контрактах, 98 детекторов, **0 находок**. Ни один reentrancy-детектор
не сработал (CEI + `nonReentrant`), в том числе на `sell()` кривой, где идёт
внешний перевод ETH на произвольный адрес.

JSON не поддерживает комментарии, поэтому обоснование каждого исключения — здесь.
Правило: заглушено ровно то, что разобрано ниже; всё остальное роняет CI
(`fail_on: low` — строже дефолта, потому что контракт неизменяем).

`"exclude_dependencies": true` — снимает находки, целиком лежащие в
`lib/openzeppelin-contracts`: `assembly` (`SafeERC20._callOptionalReturn`,
`Address._revert`), `low-level-calls` (`Address.sendValue` / `functionCall` /
`delegatecall` / `staticcall`) и `solc-version`. Это код OZ v5, а не наш.

> Почему именно этот флаг, а не `filter_paths "lib/"`, как было раньше. У них разная
> семантика. `exclude_dependencies` выбрасывает находку, только если **все** её
> элементы лежат в зависимостях. `filter_paths` — если **хотя бы один** элемент
> совпал с путём. Второй вариант опасен: настоящий reentrancy в `stake()` ссылается
> на `SafeERC20`, то есть был бы отфильтрован молча вместе с библиотечным шумом.

`"detectors_to_exclude"` — три детектора, по одному разбору на каждый (числа
находок сняты с текущего кода, после фазы 4):

- **`timestamp`** (Low, 18 находок: `MaclaurinEmission` — конструктор, `epochAmount`,
  `currentEpoch`, `emissionFinished`, `_project`, `_accrue`, `unstake`, `claim`, `exit`,
  `poke`, `rewardPerToken`, `isLocked`, `isPokeable`, `pendingUnallocated`;
  `MaclaurinCurve` — `buy`, `sell`; `MaclaurinVesting` — конструктор, `release`).
  Эмиссия по замыслу — чистая функция от `block.timestamp`; это и есть заявленная
  архитектура. Детектор ищет места, где сдвиг таймстампа даёт выигрыш. Здесь эпоха —
  604800 секунд, а сдвиг, доступный секвенсеру L2, — единицы секунд: порядка 1e-5 эпохи.
  Фаза 2 добавила сравнения с `unlockTime`, но и они измеряются неделями: сдвинуть
  разлок на секунды не даёт ничего, кроме тех же секунд начисления. Фаза 4 добавила
  ещё два класса: `deadline` в `buy`/`sell` задаёт сам пользователь и защищает он им
  себя, а `unlockTime` казны измеряется месяцами.
- **`incorrect-equality`** (Medium, 28 находок). Ложное срабатывание. 24 из них —
  ветки lookup-таблицы `epochAmount` (`n == 2` … `n == 26`): `pure`-функция сравнивает
  собственный аргумент с литеральными константами, значения вне `[2, 26]` отсекаются
  ранним guard'ом, а сама таблица закреплена тестом `test_EpochTable_MatchesSpec`.
  Остальные — сравнения с нулём: `weightTotal == 0` в `_project` (ветка «стейкеров нет»),
  две в `unstake` (в том числе `remaining == 0` — ветка «позиция закрыта полностью»)
  и `amount == 0` в `MaclaurinVesting.release` (нечего отдавать). Детектор ищет строгие
  равенства по балансам — классика вида `address(this).balance == 1 ether`, которое
  обходится force-send через `selfdestruct`. В `release` сравнение действительно идёт
  с балансом, но там это безопасно по построению: единственный получатель зашит в
  immutable, и чужой перевод на адрес казны может только увеличить его выплату
  (раздувать здесь нечего — в отличие от `MaclaurinEmission`, где расчёт от баланса был
  бы дырой). В остальных случаях сравниваются собственные счётчики контракта.
- **`pragma`** (Informational, 1 находка: «используются 2 разные версии Solidity»).
  Это `^0.8.20` в OZ v5 против `=0.8.24` у нас — прямое следствие пиннинга версии
  ради воспроизводимого билда. Реальный компилятор один и задан в `foundry.toml`
  (`solc = "0.8.24"`). Убрать срабатывание можно было бы только форком OZ.

Заодно снялся `solc-version`, который раньше глушился вручную: он жаловался, что
констрейнт `^0.8.20` захватывает версии с известными багами
(`VerbatimInvalidDeduplication`, `FullInlinerNonExpressionSplitArgumentEvaluationOrder`,
`MissingSideEffectsOnSelectorAccess`). Все три исправлены до 0.8.24, а компилятор
у нас пинован.

Ограничение прогона: slither собирает проект как
`forge build --skip ./test/** ./script/**`, то есть **ни один скрипт статическим
анализом не покрыт** — ни `Deploy.s.sol`, ни `Distribute.s.sol`, ни `Pool.s.sol`.
Для кода, который исполняется ровно один раз и необратимо, это стоит держать в уме;
их логика закрыта тестами `test/Deploy.t.sol` (6), `test/Distribute.t.sol` (22)
и `test/Launch.t.sol` (18) — и репетициями на форке.

## Machine-checked proofs

Раздел, на который ссылается [`halmos.toml`](halmos.toml). Здесь обоснование каждого
значения конфига и — честно — граница между тем, что доказано, и тем, что нет.

### Статус: не закончено

Доказательства **написаны, но полный прогон не задокументирован**. В
[`test/halmos/Formal.t.sol`](test/halmos/Formal.t.sol) 17 функций `check_*` (теоремы
A–E4), конфиг разобран построчно, но записи о завершившемся прогоне с сохранённым
выводом нет. Работа прервалась на этом месте. Считать пункт невыполненным:
`RELEASE-CHECKLIST.md` §2.4 требует прогнать руками и приложить лог — «файл существует»
не равно «доказано».

CI символьные проверки не гоняет: `.github/workflows/test.yml` — только `fmt`, `build`,
`test` и Slither. Функции названы `check_*` специально, чтобы `forge test` их не
подхватывал (он ищет `test*`, `testFuzz*`, `invariant*`), поэтому на обычный прогон
файл не влияет.

```bash
halmos --match-path test/halmos/Formal.t.sol
```

### Чем это отличается от тестов

Тест подставляет конкретные значения (или случайные, если это фаззинг) и смотрит, не
сломалось ли; пройденный тест доказывает ровно одно — на этих входах не сломалось.
halmos исполняет байткод символьно: аргумент не число, а переменная, и на каждом
ветвлении решатель проверяет достижимость обеих веток. Если ни на одном достижимом пути
не удалось подобрать значения, нарушающие утверждение, — утверждение верно **для всех
входов**. Это разница между «не нашли контрпример» и «контрпримера не существует».

Что доказывается:

| Теорема | Утверждение |
|---|---|
| A | `totalSupply()` токена неизменен при любом вызове из любого состояния хранилища — то есть `mint` не спрятан нигде |
| B, B' | `epochAmount(n) == 0` ⟺ `n` вне `[2, 26]`; члены ряда строго убывают на всём окне |
| C, C' | `multiplier(r) < E_FIXED` для всех `r ∈ [1,7]`, вне диапазона — реверт; множители строго растут |
| D, D', D'' | Сумма ряда не превосходит `EMISSION_POOL` и равна ему минус ровно 14 wei; номер эпохи ограничен при любом `block.timestamp`; цикл начисления завершается |
| E0, E1, E1' | `floor ≤ ceil` на всём домене; шаг продажи сохраняет платёжеспособность; полная ликвидация возможна всегда |
| E2 | Шаг покупки сохраняет платёжеспособность — **при явно выписанном постусловии двоичного поиска** |
| E3, E3' | Цена монотонно не убывает; вне области определения `priceAt` ревертит, а не врёт |
| E4 | Ни одна точка входа кривой, кроме `sell`, не может уменьшить `reserve` — в том числе `withdrawFees` |

### Значения в `halmos.toml`

- **`loop = 26`** — граница разворачивания циклов, и это единственная настройка,
  решающая, доказательство перед нами или проверка до глубины N. Здесь она подобрана
  так, что разница исчезает: оба цикла `MaclaurinEmission` ограничены immutable-константами
  байткода — `totalEmittable()` делает ровно 25 итераций (`FIRST_EPOCH..LAST_EPOCH`),
  `_project()` не может пройти больше 25 сегментов, потому что останавливается на
  `emissionEnd`. При 26 halmos разворачивает обе петли целиком и не сообщает о
  достигнутой границе, так что «ограниченное символьное исполнение» совпадает с
  исчерпывающим. Предупреждение о достигнутой границе в выводе = результат недействителен.
- **`solver = "yices"`** — быстрее z3 на битвекторной арифметике, которая здесь
  доминирует.
- **`solver-timeout-assertion = 300000`** (мс) — без бюджета на утверждение нелинейный
  запрос (площадь трапеции в `MaclaurinCurve`) висит вечно, и «не досчитали» становится
  неотличимо от «верно».
- **`solver-timeout-branching = 20000`** — условие ветвления обязано решаться быстро;
  если не решается, путь больной.
- **`width = 0`** — никакого потолка на число путей: любая ненулевая граница молча
  превратила бы доказательство в выборку.

Файл намеренно ASCII-only: halmos 0.3.3 открывает его с кодировкой платформы по
умолчанию (на Windows — cp1252), и любой не-ASCII байт роняет инструмент до старта.
Поэтому обоснования вынесены сюда, где ошибка кодировки не ломает сборку.

### Граница честности

Внутри `buy()` стоит двоичный поиск `MaclaurinCurve._tokensFor` — около 90 итераций,
на каждой ветвление, то есть `2^90` путей. Символьно исполнить это нельзя ни halmos,
ни чем-либо ещё, и притворяться, что доказано, нельзя тоже. Поэтому:

- шаг **продажи** доказан полностью — в этом пути циклов нет;
- шаг **покупки** доказан при явно выписанном постусловии поиска
  (`quoteBuyCost(d) ≤ netIn`) — то есть доказана вся арифметика вокруг него, кроме
  самого поиска;
- ключевая лемма `floor ≤ ceil`, на которой держится весь инвариант
  платёжеспособности, доказана отдельно и на всём домене.

**Что остаётся непроверенным машиной:** что двоичный поиск действительно обеспечивает
своё постусловие. На это работают обычные тесты, включая дифференциальные и фаззинг.
Это тесты, а не доказательство, и выдавать одно за другое здесь не будем.


Разворачивается только `MaclaurinEmission` — токен он создаёт сам в конструкторе,
поэтому пул эмиссии ни на один блок не оказывается под приватным ключом.

Прогнать полный цикл вручную: `stake` с R=1 → убедиться, что `claim()` ревертит
`StillLocked` → дождаться разлока → `claim` → `unstake` → `exit` → `poke` →
`sweepToRemainderVault`. Успешный `claim()` и `poke()` на истёкшей позиции в живой сети
не проверить (`EPOCH_DURATION` — `constant`), для них есть локальный форк с
`evm_increaseTime`.
